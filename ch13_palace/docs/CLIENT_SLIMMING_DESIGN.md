> 日期：2026-11-22　配套：`docs/CLIENT_COMPAT_ASSESSMENT.md`、`tools/XLSX_PIPELINE.md`

## 0. 摘要

原始版本不是"没设计"，恰恰相反——它有 MVC、有命令层、有绑定、有 actor 化的服务端、有配表代码生成。**它的问题是把同一份契约在四个地方各声明了一遍**：

| 事实 | 原服声明点 | 客户端声明点 | 精简版声明点 |
|---|---:|---:|---:|
| 一个 op 的参数与含义 | 2（常量 + `@Rpc` 注解） | **4**（常量 + 方法 + 注册 + 分发） | 1（schema 一行） |
| 一个字段的类型与含义 | 4（VO 字段 + getter + 构造 + 序列化） | **4**（BindableProperty + getter + 解包 + UI） | 1（schema 一行） |
| 一张配表 | 1（Excel → 279 个 Java 类） | 1（Excel → 319 个 JSON） | 1（xlsx → Lua table） |

三端代码量的差距不来自功能，而来自**声明点的数量**：

- 原服 525,578 行里 **298,071 行（56.7%）** 是配表生成的 Java 静态类——"生成"它做了，但生成目标选错（强类型类 → 编译期膨胀）
- 客户端 152,386 行里 **59,172 行（38.8%）** 是窗口本体（内容，不可删），**31,145 行（20.4%）** 是 VO 镜像 Model（可生成/删除）
- 精简版 2,000 行承载同样的契约，代价是把"编译期校验"换成了"运行时校验"

**结论三条：**

1. 精简的目标不是删功能，是**让每个事实只被声明一次，其余生成**。可净减 **4.5~5.0 万行（约 32%）**。
2. **原服最值得学的是 `@Rpc` 注解路由**——op 与实现绑在一处，636 个处理器因此能铺开；客户端恰恰把同一份路由拆成常量、方法、注册、分发四处，这才是"臃肿"的真正定义。更隐蔽的浪费是：同一串 op 在两端各存一份副本（595 / 290），无人校验一致。
3. **最大的风险不是技术，是迁移期的双真相**。新 store 与老 Model 并存必须"双读单写"，否则会出现最难查的一类 bug。

## 2. 核心发现：三端同构，差距只在"声明点"

### 2.1 op 是"注解声明 + 两端各存一份副本"（证据链）

```ts
// 客户端 ClientNetConst.ts：290 个常量，全部 u.* 前缀
REQ_USER_LOGIN = "u.login"
REQ_ITEM_SALE  = "u.itemSale"
```
```java
// 原服 GongRpcConstants.java：1,487 行，595 个 u.* 常量
public static final String REQ_USER_ITEM_SALE = "u.itemSale";

// 原服 UserProxy.java：注解声明路由，参数按类型反射绑定
@Rpc(fullAlias = GongRpcConstants.REQ_USER_ITEM_SALE)
public void itemSale(ServerChannelContext ctx, RpcResult rpcResult, String itemMapJson)
```

三个事实：

1. **原服的 op 只声明一次**（方法上的 `@Rpc` 注解），参数由框架按类型绑定。这已经是"注册制"，与精简版 `schema.handler → require("handler.x")` 同一思想——**服务端的设计是对的**。
2. **但同一串 `"u.itemSale"` 在两端各存一份**：服务端 `GongRpcConstants` 595 个、客户端 `ClientNetConst` 290 个（约占服务端 49%），**共 885 行常量，没有任何机制校验它们一致**。改一个 op 要改两个仓库。
3. **客户端为什么用位置参数**——它照抄 Java 方法签名。服务端把 `String` 改成 `int`，客户端静默失效，因为类型契约只存在于人的记忆里。

这就是"契约没有单一事实源"的完整含义：不是没人管，而是**管了两次**。

### 2.2 一个 op 的声明点：2 vs 4

| 环节 | 原服 | 客户端 |
|---|---|---|
| 常量定义 | `GongRpcConstants` 一行 | `ClientNetConst.ts` 一行 |
| 路由声明 | 方法上 `@Rpc(fullAlias=常量)` | `ServerNetConst.ts` 注册一行（仅推送） |
| 发送方法 | 方法签名（参数按类型绑定） | `ClientProxy.ts` 方法或裸 `send("u.xxx", ...)` |
| 分发实现 | 方法体（与路由同一处） | `ServerCommand.ts` 一个方法 |

原服加一个 op = 常量 + 注解 + 方法，**三样在同一个仓库、同一个 PR 里，注解本身即路由**。客户端加一个 op = 改 3~4 个文件 + 对一次参数顺序，且请求侧的路由（`send` 的 op 字符串）根本没有声明，只有运行期才知道对错。

**这就是 595 个 op 只能在服务端铺开、客户端却始终只覆盖一半的原因。**

### 2.3 一个字段的声明点：4 vs 4 vs 1

| | 声明点 |
|---|---|
| 原服 | VO 字段 + getter + setter + `toJson` 里的字段名 → 4 |
| 客户端 | `BindableProperty` 声明 + getter + `onChangeAvatar` 解包 + UI 读取 → 4 |
| 精简版 | schema 一行（`fid/name/type/partition/persist/replicate`） → 1 |

`AvatarModel.ts` **345 行只描述 62 个字段**，全工程 `BindableProperty` 引用 **1,461 处**。这不是"代码多"，是"同一个事实写了四遍"。

### 2.4 配表：原服已经生成，但生成目标错了

原服 `palace-common/common/config/data` 下 **279 个 Java 类 / 298,071 行**（占全服 56.7%），与客户端 319 张 JSON 一一对应（`ActivityData.java` ↔ `ActivityData.json`）。

也就是说：**两端本来就同源**（同一份 Excel，一次导 Java、一次导 JSON）。真正的浪费是：

- 生成物是**静态强类型类** → 每个字段一个 getter/setter，279 张表膨胀成 29.8 万行，编译慢、包体大
- 生成物**启动全量装载**（`DataUtils.checkData()`）→ 内存常驻
- 客户端 JSON 是**全字段导出** → 语言表 4.7MB 也进包

精简版的做法是"生成数据，不生成代码"：xlsx → Lua table（运行时读），同一个 279 张表在服务端只占硬盘与内存，不占代码行。

**这是三端最大的结构性差异，也是"精简"最有说服力的一笔账。**

## 3. 原版本做对了什么（必须先保住）

| 机制 | 端 | 它解决什么 | 为什么不砍 |
|---|---|---|---|
| **Entity 串行执行**（guardian gas） | 服 | 每个玩家一个 Entity，方法调用串行化，天然无锁 | 与 skynet actor 同构，是并发正确性的地基；改成就地多线程等于重写 |
| **`@Rpc` 注解路由** | 服 | `@Rpc(fullAlias)` 把 op 与实现绑在一处，加 op 不改框架 | 636 个处理器全靠它铺开；这是原服最值得抄的一招 |
| **配表代码生成** | 服 | 两端同源，字段名不漂移 | 方向完全正确，只是生成目标该改 |
| **Proxy 分层**（46 个） | 服 | 按业务域切分协议入口 | 客户端对应位置缺失，才导致 64 个方法挤在一个类里 |
| **栈式窗口 + 暂停/恢复** | 客 | 返回栈、遮罩、暂停是产品行为 | 换路由也要保留栈语义 |
| **细粒度绑定** | 客 | 货币变了只刷一个 Label | 换整树重绘会掉帧；要改的是写法不是机制 |
| **客户端本地预演** | 客 | 0 延迟手感、弱网可继续 | 砍了就变成"点一下等 200ms" |
| **Command 层** | 客 | 一次交互封装成可复用单元 | 方向对，问题是 1/3 只做了一次转发 |

一句话：**架构方向全对，执行方式全是手抄。**

## 4. 客户端精简设计

### 4.1 目标形态：三层 + 一个生成器

```
               conf/schema.xlsx  ←—— 唯一事实源（与原服/精简版同一份）
                        │
                 gen_client.py
                  ┌─────┼──────┐
                  ▼     ▼      ▼
              ids.ts  types.ts  routes.ts
                  │     │      │
   ┌──────────────┴─────┴──────┴──────────────────┐
   │ L1 wire   codec.ts    ~250 行   7 种 kind     │
   ├──────────────────────────────────────────────┤
   │ L2 state  store.ts    ~600 行   fid + rev     │
   ├──────────────────────────────────────────────┤
   │ L3 view   router.ts   ~200 行 + 279 窗口      │
   └──────────────────────────────────────────────┘
```

- **wire 只认 kind（1~7），不认 op**：op 是边缘兼容物，进 L1 立刻翻译成 `aid`
- **state 只认 fid**：字段含义由 schema 赋予，客户端不再持有"业务字段清单"
- **view 只认 selector**：窗口订阅 `fid=4`（gold），不认识网络

### 4.2 L1：codec 取代 290 常量 + 64 分发方法

```ts
// 示意，未落地
export interface Envelope { kind: number; seq?: number; aid?: number; params?: any }

export class Codec {
  req(op: string, params: Record<string, any>, cb?: (r: any, err?: number) => void): void;
  on(kind: number, fn: (e: Envelope) => void): void;
  private normalize(raw: any): Envelope;   // 老信封 {id,type,op,error,params} → Envelope
}
```

- `ClientNetConst.ts`（290 常量）→ `ids.ts`（生成，保留字符串供老代码引用）
- `ClientProxy.ts`（55 方法）→ 保留 12 个有业务语义的，其余走 `codec.req(ids.X, {...})`
- `ServerCommand.ts`（64 方法）→ **删除**，改 `store.apply(envelope)`
- 参数从**位置数组**改**命名对象**——影响只在客户端内部，服务端 `message.normalize_in` 已能按 `action.params` 还原

### 4.3 L2：store 取代 364 个 Model

```ts
export class Store {
  private fields: Map<number, any>;   // fid -> value
  private rev = 0;
  applySnapshot(s: { rev: number; partitions: Record<string, any> }): void;
  applyDelta(d: { base_rev: number; rev: number; mask: number[]; values: any }): boolean;
  get<T>(fid: number, def?: T): T;
  watch(fid: number, fn: (v: any, old: any) => void): () => void;
}
```

364 个 Model 的去向，逐个交代：

| 类型 | 数量（估） | 处理 |
|---|---:|---|
| 纯 VO 镜像（62 字段摊平） | ~180 | **删除**，改 `store.get(fid)` |
| 派生模型（战力、红点、可合成判断） | ~110 | **保留**，内部改读 store，对外 API 不变 |
| 本地临时态（选中、页签、排序） | ~70 | **保留**，本来就是 UI 状态 |

**不是删 364 个类，是删掉 180 个"只转发服务端字段"的。**

rev/delta 落地就是**删消息**：56 个推送 op 里约 20 个（`item_change`/`hero_change`/`building_change`/`mission_change`…）本质都是"某个 map 或标量变了"，统一成 `u.delta` 后：20 个 op → 1 个，20 套增删改合并 → 1 套。

### 4.4 L3：路由表取代字符串反射

```ts
// routes.ts —— 生成
export const ROUTES = {
  LevelUpWnd: { prefab: "Prefabs/LevelUpWnd", tables: ["LevelData"], fids: [3, 4], keep: false },
  BagWnd:     { prefab: "Prefabs/BagWnd",     tables: ["ItemData"],  fids: [7],   keep: true  },
} as const;
```

收益是三件具体事，不是"更优雅"：
1. **依赖预加载**：44 处手写 `loadDataList` 消失
2. **包体裁剪**：500 个 prefab 对应 279 个窗口类，**剩下 200 多个是什么目前无人知道**——建表过程本身就会暴露这批死资源
3. **静态校验**：`fids` 必须在 schema 里存在，配错在构建期报错

### 4.5 配表：按"谁真的需要"三切（有实证）

实测两端表集：**服务端 279 张 / 客户端 319 张 / 交集 251 张**。

| 类别 | 数量 | 代表 | 处置 |
|---|---:|---|---|
| 交集（双端都要） | **251** | `ItemData`、`ActivityData`、`BagData` | 同源导出，各取所需列 |
| 仅客户端（纯表现） | **68** | `LanguageTextData`(4.7MB)、`AudioData`、`StoryGroupData`、`HomeNpcwalkData`、`TabooTalkData1-3` | 服务端不需要，**不进服务端包** |
| 仅服务端（纯规则） | **28** | `SkillFormulaData`、`DropItemData`、`FightBgData`、`RoleSkinData` | 客户端不参与结算，**默认不进客户端包**（战斗预演需要的除外） |

现在的问题不是"两端不同源"（原服同源），而是**交集 251 张两端各存全列**：`ItemData` 1568 条，服务端只要 `id/type/quality/stack`，客户端要 `name/icon/desc/source`，两边各存一份完整表，改道具要手动同步两次。

建议方向（不改代码，只定方向）：**上游是客户端那份**（玩家看到的是权威），服务端用 `tools/gen_gamedata_from_client.py` 反向抽取规则列。现有 `gamedata.xlsx` 只有 4 英雄 / 7 道具，与客户端 27 / 1568 完全脱节——这个缺口不补，任何"精简"都是空中楼阁。

## 5. 机制分析

A 组是既有机制（含原服），B 组是精简设计引入的新机制。每条给**优点、代价、取舍、边界**。

### A 组

#### A1. Entity 串行执行（guardian gas）

- **做法**：每个玩家一个 `AvatarEntity`，业务方法挂在 service 上，经 Entity 串行队列执行（API 形状：`Entity` / `EntityCallback` / `GasManager`；引擎 jar 未随仓库提供，此处为 API 推断，与 skynet actor 同构）
- **优点**：单玩家状态无锁；业务代码可以像单线程一样写 `if/else`；崩溃隔离到 Entity
- **代价**：跨 Entity 交互必须走异步回调（`onResult` 嵌套 3~4 层，`UserProxy.login` 一段 100 行里有 3 层回调）；调试栈深；无法利用多核（靠"多进程 + 多 Entity 分片"横向扩）
- **取舍**：**保留**。这是并发正确性的地基。精简版用 skynet actor 复刻了同一语义，代价是 Lua 无静态类型
- **边界**：跨服/跨 Entity 的操作（公会、跨服战）必须显式定义"两阶段提交"或"最终一致"，不能靠回调嵌套兜住

#### A2. `@Rpc` 注解路由 + 两端常量副本

- **做法**：`@Rpc(fullAlias = GongRpcConstants.REQ_USER_ITEM_SALE)` 标在 `UserProxy.itemSale(...)` 上，框架扫描注册，参数按类型绑定
- **优点**：路由与实现同一处，加 op 零框架改动；636 个处理器（含内部 RPC）能铺开全靠它；客户端只需一个字符串
- **代价**：① 参数靠**位置 + 类型反射**，改类型不报错；② `UserProxy` 单文件上千行，507 个方法挤在 46 个 Proxy 里；③ 无法表达可选参数/默认值；④ **op 字符串在两端各存一份**（595 vs 290），无一致性校验
- **取舍**：**思想保留，载体改造**。精简版把"注解 + 常量"换成 schema 一行 + handler 一个：同样一处声明，但参数有名字、有校验、两端可生成
- **边界**：若短期不换载体，最低成本补丁是让客户端从服务端常量表**生成** `ClientNetConst.ts`（而非手写），并附带参数类型指纹；这一条改动量极小，收益立即兑现

#### A3. 配表生成 Java 静态类

- **做法**：Excel → 279 个 Java 类（298,071 行），启动全量装载
- **优点**：编译期有类型；IDE 可跳转；字段改名全局报错——**这是客户端最缺的东西**
- **代价**：占全服 57% 代码量；编译慢；包体大；表现层文本也生成（服务端根本不用）
- **取舍**：**服务端改运行时读表，客户端保留类型**。两端目标不同：服务端要"省内存省编译"，客户端要"编译期校验"
- **边界**：客户端生成 `types.ts` 时只生成**契约字段**（fid + 类型），不生成 319 张表的全部实体类，否则就是把 Java 的坑换个语言再踩一遍

#### A4. VO 全量直通 + add/update/delete 列表

- **做法**：`AvatarVO` 整个 JSON 下发 + 变更推三个列表
- **优点**：服务端零成本，`ObjectMapper` 一把梭——**281 个 op 能快速铺开就是靠这个**
- **代价**：客户端 62 字段全量重建；20 余套增删改合并逻辑重复；无法表达"替换/排序"语义；流量随背包线性增长
- **取舍**：**分阶段替换**。保留 VO 作 `wire=1`，新增 `wire=2`（snapshot/delta）
- **边界**：`bag`(1568 条)/`heroes` 目前 delta 是**整字段粒度**，一次买道具重传整个背包。必须先做"map 内 key 级 delta"再切，否则流量反涨

#### A5. BindableProperty 细粒度绑定

- **做法**：每字段一个 `BindableProperty`，UI 订阅 `.onChange`
- **优点**：精准刷新不重建节点树，方向正确（1,461 处使用说明吃到了甜头）
- **代价**：62 字段 ×（声明 + getter）= 250 行样板；改名改三处；`AvatarModel.ts` 345 行里 90% 是样板
- **取舍**：**机制保留，声明生成**
- **边界**：生成代码不可手改，必须带文件头 + `make check` 一致性门禁，否则半年后无人记得

#### A6. 栈式窗口 + 字符串反射加载

- **做法**：`pushWnd(name)` 运行期拼路径 + 压栈 + `pauseWnd`
- **优点**：栈语义干净；`pathMap` 缓存避免重复加载
- **代价**：279 个窗口无路由表，构建期不知可达性；依赖靠 44 处手写；改名不报错
- **取舍**：**保留栈，补路由表**（纯新增，风险极低）
- **边界**：动态窗口（按活动 ID 拼名）必须登记 `dynamic: true`，否则裁剪误删

#### A7. 全局单例 + 字符串事件总线

- **做法**：21 个 `XxxService.getInstance()`，743 个事件名，740 个收发点
- **优点**：解耦彻底，加监听不碰既有代码
- **代价**：**隐式耦合**——"谁在听 `EVENT_ITEM_CHANGE`"只能全局搜索；顺序无保证；重入无保护
- **对照**：同一个团队，服务端的 `gas/eventbus` 只有 **2 个事件类**（`LoginEvent`/`CardInfoEvent`）、**14 个使用点**。差别不在人，在结构——服务端有"方法调用"这条主通道，事件只用于真正的广播；客户端 UI 之间没有主通道，只能全部走事件，于是事件成了万能胶，也成了万能债
- **取舍**：**保留总线，收敛事件源**。事件名从 schema 派生（`evt.field.<fid>` / `evt.action.<aid>`），Service 降级为 store 之上的领域门面；UI 之间的一对一通知改直接调用或 store 订阅
- **边界**：**不要用事件替代 store 订阅**。事件是"发生了"，store 是"现在是什么"；混用必出"事件到了数据没到"

#### A8. 客户端本地预演（战斗/经营双状态机）

- **做法**：客户端也算一遍，服务端再算权威结果
- **优点**：0 延迟手感，这是体验硬需求
- **代价**：两套规则、两份 bug、对账差异（原服"经营对账"是历史顽疾，`ManagerExchangeData` 这类表就是为对账而生）
- **取舍**：**保留预演，明确权威**。规则抽成纯函数（状态 + 参数 → 状态 + 事件），服务端 Lua / 客户端 TS 两个运行时，配对账用例
- **边界**：**随机数必须服务端给种子**。不解决这条，预演只能做动画不能做结算

#### A9. 断线重连 = 全量重建

- **做法**：`onClose` 清空 `_cbTable`，重连后重走 `u.login` + 全量拉
- **优点**：简单不会错，没有"半新半旧"
- **代价**：3~5 秒；未决回调全丢
- **取舍**：短期保留，中期换 rev（`u.snapshot?since=rev` 返回差量）
- **边界**：rev 不匹配必须有"拉全量"兜底，否则会"永远差 1"

### B 组：新增机制

#### B1. schema 单一事实源 + 生成

- **优点**：一处声明两端受控；新增 op 从"改 4~5 处"降到"改 1 行"
- **代价**：生成器成为单点（有 bug 两端一起错）；生成物不可手改；缺门禁就静默漂移
- **取舍**：采纳，加三道闸——文件头指纹、`make check` 进门禁、生成器自带单测
- **边界**：**表现层不要进 schema**。布局/动效/颜色进 schema 会把"契约"变成"配置地狱"——这正是 319 张表混装的教训

#### B2. 信封 kind 化（7 种取代 300 余 op 分支）

- **优点**：分发从"op 查表"变"kind 分支"；新业务不再新增信封类型
- **代价**：老客户端不认（`type` 是字符串、`error=200`）；迁移期必须双信封
- **取舍**：采纳，`normalize()` 入站统一转 kind，出站按协商能力决定
- **边界**：`error` 语义（0 vs 200）**绝不能全局改**，只能在出站适配层映射——229 个断言依赖 200

#### B3. rev / delta + 能力协商

- **优点**：推送 op 从 56 收敛到 ~10；重连变增量；幂等
- **代价**：服务端维护 rev 与脏分区（已实现）；客户端维护本地 rev（`client_state.lua` 已给参考但未移植）；map 整字段 delta 是流量炸弹
- **取舍**：先标量后 map
- **边界**：WS over TCP 不丢包、不乱序——**rev 的真正价值不是防乱序，是断线差量与幂等**。这点要写进团队共识，否则会被当过度设计砍掉

#### B4. 声明式视图路由

- **优点**：预加载自动、包体可裁剪、依赖可校验
- **代价**：路由表要维护；动态窗口要标记；窗口类与 prefab 靠命名约定，未必 100% 对齐
- **取舍**：先只用于预加载（低风险），裁剪等有可达性分析再做
- **边界**：路由表建设会暴露 500 − 279 ≈ 221 个无主 prefab，这是额外收益，但清理要先确认不是运行时拼名加载的

## 7. 落地阶段（S0~S4，均不动现有代码）

| 阶段 | 内容 | 产出 | 风险 |
|---|---|---|---|
| **S0** | 契约反向抽取：从 `ClientNetConst`(290) + `ServerCommand`(64) + 原服 507 个方法签名，反推参数表并入 `schema.xlsx`（只加元数据） | `docs/CONTRACT_MATRIX.md` + schema 扩展 | 低（纯文档） |
| **S1** | `gen_client.py`：schema → `ids.ts` / `types.ts`，接 `make check`；不改业务代码，只生成新文件 | 生成器 + 门禁 | 低（旁路） |
| **S2** | `codec.ts` + `store.ts`：**双读单写**——新 store 从老推送喂数据，老 Model 继续工作 | 兼容层 | 中（双写风险） |
| **S3** | 逐域替换 item → hero → mission，每域留回退开关；20 个变更推送并入 `u.delta` | 灰度开关 | 中高 |
| **S4** | 路由表 + 预加载 + 包体裁剪 + 语言表分包 | 构建期分析 | 中 |

## 8. 风险与明确不做

| 风险 | 影响 | 缓解 |
|---|---|---|
| 双读期出现两份真相 | 偶发数据错乱，最难查 | 严格单写：只有 store 接收网络，老 Model 只做投影 |
| 生成器与源表漂移 | 两端静默不一致 | `make check` 进门禁 + 文件头指纹 |
| `error` 语义被全局改 | 229 个断言全崩 | 只在出站适配层映射 |
| 语言表分包影响老包 | 老版本找不到文本 | 分包只对新包生效 |
| 预演规则双写不一致 | 结算对账差异 | 服务端下发随机种子 + 对账用例 |
| 原服 595 个 op 中有 305 个客户端未调用 | S0 抽取时误判为"废弃"而漏记 | 抽取时区分"未调用"与"已废弃"，后者需人工确认 |
| 两端 op 常量表（595 / 290）长期漂移 | 改 op 忘改另一边，线上 404 | 改为从服务端常量表生成客户端 `ids.ts`，纳入 `make check` |

**明确不做**：
- 不重写 UI 框架（Cocos 组件生命周期与 `WindowRoot` 绑定太深）
- 不动 `BindableProperty` 实现（只改声明方式）
- 不把表现层配置塞进 schema
- 不用事件总线替代 store 订阅
- 本轮不改任何一行代码

## 9. 结论

**原服把"契约"放对了地方（方法签名），但生成物放错了形态（29.8 万行静态类）；客户端把"架构"搭对了骨架（MVC + 命令 + 绑定），却把契约手抄了四遍。两者合起来就是 67 万行代码里约 6 万行是纯重复声明。**

精简的实质只有一句话：**契约变成数据，代码只描述行为。** 可减约 32% 代码、5 成边际改动面、4 成配表体积；真正的难点不在技术，而在"双信封 + 双读单写 + 灰度开关"这套迁移纪律，以及把客户端配表确立为服务端配表的上游这一尚未补齐的前提。
