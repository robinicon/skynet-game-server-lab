# ch7_db 修复记录

---

## 1. mock 驱动不 yield → 并发测试是假绿的（最危险的一条）

**现象**：如果 memory 驱动写成纯同步（不 yield），"并发存盘"用例会全部通过——
因为单线程 Lua 的读-改-写在没有 yield 点时**天然原子**，丢失更新根本不会发生。

**风险**：这不是"测试通过"，是"测试什么都没验证"。
真实 MySQL 查询一定会 yield（网络往返），所以 mock 必须模拟这个 yield。

**修复**：`shared/db_driver.lua` 的每个操作先 `skynet.sleep(latency)`，
`latency` 可配置（tick 数，1 tick = 10ms）。

**并且把"对照组必须失败"写成断言**：

```lua
-- C1.2：对照组（无 queue）**必须**丢失更新，否则说明测试无效
check("C1.2 control group LOSES updates (proves the test is meaningful)",
    hp_u < N, string.format("hp=%d N=%d", hp_u, N))
```

实测对照组 hp=1（N=20），丢失 19 次更新 —— 证明交错窗口真实存在。

**教训**：异步系统的 mock 必须复现**调度语义**（yield 点），不只是复现返回值。

## 2. 等待并发任务完成必须有超时上限

**现象**：沿用 ch4 的教训。`while done < n do skynet.sleep(1) end` 在任一协程异常时会永久挂死。

**修复**：`wait_done()` 带 `limit_ticks` 上限（默认 2000 tick = 20s），
超时返回 false 由调用方判失败，而不是继续等。

---

## 3. 写合并后 save_sync 会写回旧数据（设计阶段预判并规避）

**风险分析**：引入写合并后，`save_async` 的数据会暂存在 `pending[uid]`，
由 fork 出的 flush 协程延迟落盘。若此时 `save_sync` 直接写自己的数据，
而 flush 协程稍后才写 `pending`（旧数据），最终状态会是**旧的**。

**规避设计**（三条规则）：

1. `save_sync` 接管 `pending`：合并未落盘数据，一次性写完，并清空 `pending`
2. flush 协程醒来发现 `pending` 为空 → 跳过
3. flush 与 `save_sync` 共用同一条 `serial(uid)` 队列

**验证**：`C3` —— 10 次 `save_async(hp=1..10)` + 1 次 `save_sync(hp=999)`，
最终必须是 999。实测通过。

---

## 4. 连接池等待不能用轮询

**风险**：`while not conn do skynet.sleep(1) end` 会引入 **10ms 粒度**的固定延迟，
在高频存盘场景下放大成严重的性能问题。

**修复**：用 `skynet.wait(co)` / `skynet.wakeup(co)`，token 用协程对象。
`release` 时若有等待者，直接交给它（先入 free 再唤醒，唤醒方从 free 取）。

---

## 5. 环境无 MySQL，需要可回归的替代方案

**现象**：WSL 环境没有 mysqld，skynet 虽有 `skynet.db.mysql` 但连不上。

**处理**：驱动抽象成两层（`shared/db_driver.lua`）：

- `memory`：内存表 + 注入 yield，默认，保证 37 个用例可无依赖回归
- `mysql`：封装 `skynet.db.mysql`，`CH7_DB_DRIVER=mysql` 切换

两者实现同一组**语义级**接口（`load_role` / `save_role` / `delete_role`），
而不是 SQL 字符串级接口 —— 这样 memory 实现不需要写 SQL 解析器。
