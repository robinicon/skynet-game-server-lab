## 01 · [Skynet 手记] 登录链路拆解：Frame 信封、opcode 与服务端分发

**证据出处**：`docs/设计文档/02-协议与信封设计.md`、`docs/功能系统文档/01_网络与协议层.md`、
`docs/施工计划/skynet版本施工计划.md §1.3`、`legend3D/server-skynet/lualib/engine/opcode.lua`、
`service/gated.lua`、`service/authd.lua`

**开篇钩子**：一次「登录失败」排障，抓包发现客户端发的字节和服务端解出来的 opcode 对不上——
不是密码错，是 `4B len + 2B opcode + payload` 的帧头约定没对齐。

**章节结构**：
1. 开篇：一个对不上的 opcode（真实现象 + 抓包字节）
2. Frame 信封：为什么是 `4B len + 2B opcode`；skynet `netpack` 默认 2 字节头为何不够用 → 自写
   `cmod/mmo_netpack.c`（skynet 计划 1.3 的原始决策）
3. opcode registry：只增不改的纪律；注册与校验器（协议层文档）
4. protobuf 单一 schema：双端只认一份 `.proto`，`lua-protobuf` 加载；不引入 sproto 的理由
5. 服务端分发：`gated` 收包 → 表驱动分发 → `authd`；五类通道语义
6. 一次登录的字节级时序（0x0B03/0x0B04 等，引用协议文档的真实 opcode）
7. 复盘：协议先定义再写代码；双端共享单一 schema；帧头别用框架默认值
8. 已知环境限制：只覆盖登录链路；未涉及战斗/同步 opcode；抓包环境说明
9. 代码与运行：`server-skynet/` 目录树、协议笔测试命令

**配图**：封面（科技蓝）+ Frame 信封结构图 + 登录时序图（本地绘图）
**数据说明**：opcode 与帧头格式来自设计文档；字节示例为取证记录，标注来源。

## 03 · [Unity 手记] 满屏白块不是渲染 bug：UGUI 的 `Image.sprite==null` 会画白矩形

**证据出处**：`docs/分析报告/NGUI-UGUI迁移现状与修复方案.md §3.1`、
`docs/分析报告/evidence/login_system_view_white.png`、`login_system_view_ui_ok.png`

**开篇钩子**：启动游戏，登录界面是一整块白。查 shader、查相机、查渲染管线，最后发现
「白块」是 UGUI 自己的行为：`Image.sprite == null` 时会绘制一张**不透明纯白矩形**。

**章节结构**：
1. 开篇：一张白屏截图（引用真实证据图）
2. 现象与排查路径：先排除渲染管线 / 相机 / shader
3. 根因：NGUI 里「没 sprite 就不画」的 `UISprite` 被转成 UGUI `Image`，后者 `sprite==null`
   画白矩形；11 个空 Image、5 个近全屏叠出白屏（报告原始数据）
4. 验证：临时把这些 Image 的 alpha 置 0 → 底图/LOGO/文案全部正常（before/after 对照截图）
5. 为什么这类 bug 难查：编译器和 Console 都不报错，是「静默缺陷」
6. 复盘：不报错≠没问题；数据迁移要理解目标组件的语义差异；建可截图的对照实验
7. 已知环境限制：Unity 2021.3；仅登录面板取证；转换工具版本说明
8. 代码与运行：定位空 Image 的检查脚本思路（引用报告方法）

**配图**：封面 + **真实 before/after 截图**（直接引用 evidence 目录）
**数据说明**：11 个 / 5 个等数字来自迁移报告，标注出处。

## 04 · [Unity 手记] 59 个界面只接了 1 个：NGUI→UGUI 迁移为什么是场持久战

**证据出处**：`NGUI-UGUI迁移现状与修复方案.md §2.2/3.2/3.3/3.4/3.5`

**开篇钩子**：NGUI 引用全清零、工程能编译、登录面板还能显示中文——看起来迁移完成了。
但 59 个界面里只注册了 1 个，17/92 个 Graphic 跑到画布外。

**章节结构**：
1. 开篇：「骨架换了、皮肉没接上」的现状（报告原话）
2. 三套东西并存：转换产物 / UGUI 基础设施 / 接入层
3. 锚点体系换算：100×100 根节点归一化导致 `anchorMin=-5.675`；NGUI 左下原点 vs UGUI 中心原点；
   17/92 越界（报告 §3.2）
4. 交互控件没接：4 个 ScrollRect 全是 viewport=100×100、无 Mask，列表「既滚不动又溢出」（§3.3）
5. CanvasScaler 只按宽度适配：1440×740 下逻辑高度 657.78，比 720 少 62px，顶部/底部被裁（§3.4）
6. 面板接入：59 个只接了 1 个；关键路径是 3231 个 Image、540 个 Button、23 个 ScrollRect
   的人工复核
7. 复盘：迁移分层验收（清障→静态→锚点→交互→接入→回归）；资源格式转换≠表现层完成
8. 已知环境限制：截至报告取证时的 Sprint；Game View 1440×740；未覆盖全部面板
9. 代码与运行：报告 §6 六阶段修复方案摘要

**配图**：封面 + 锚点越界示意图

## 05 · [Unity 手记] 每次登录第一次必失败：一次连接竞态的完整追杀

**证据出处**：`docs/分析报告/回并修复日志.md` F030、F028、F022、`_diag_net.log`

**开篇钩子**：不是偶发——每个登录周期，第一次进服**必定失败一次**，第二次就好了。
这种「有规律地必错」比随机 bug 更值得追。**注意：现象在服务端日志最明显，但根因与修复全在客户端
`GTCPConnectionClient.cs`（未清 `_stream` + 旧回调误杀新连接），故归入 Unity 手记。**

**章节结构**：
1. 开篇：可稳定复现的「首次必失败」现象（日志摘录）
2. 时间线还原：旧连接的读回调在新连接建立后才触发，误把新连接判为失败（F030 竞态）
3. 为什么是「必失败」而不是偶发：事件顺序在登录周期里是固定的
4. 一个误导性线索：Gate 日志 0 字节 ≠ 无连接（F022）——日志口径差点带偏排查方向
5. 相关分流修复：未进过 GameServer 的周期不再发 0x1004（F028）
6. 修复方案与验证：连接代际标记 / 回调归属校验（按 F030 实际修复方式写）
7. 复盘：竞态按时间线还原；日志口径别想当然；「必现」比「偶现」更好查
8. 已知环境限制：localhost 建连约 1ms 的时序前提；修复位置在客户端，服务端未改
9. 代码与运行：`GTCPConnectionClient.cs` 代际隔离、`LegendGame.cs` 等待收尾、`_diag_net.log` 取证入口

**配图**：封面 + 竞态时序图（旧/新连接回调交错）
**数据说明**：竞态过程引用 F030 原文；日志示例标注文件名，不虚构时间戳。修复位置据实为客户端。

## 06 · [Unity 手记] 重连不是「接着玩」：客户端重连状态机该怎么设计

**证据出处**：`docs/设计文档/05-客户端总体设计.md §3.3`、
`.screenshots/o08_reconnect*`、`.screenshots/o08_reconnect_fail*`

**开篇钩子**：玩家网络抖一下，客户端显示「已重连」，但角色像「回档」几秒——
因为服务端语义是「重连 = 新会话，不恢复旧状态」，客户端却当成原地继续。

**章节结构**：
1. 开篇：重连后「回档」的现象（重连截图）
2. 服务端语义：重连是新会话（05 §3.3 明确），客户端必须接受这点
3. 状态机四态：CONNECTED → RECONNECTING（指数退避 1/2/4/8/16s，上限 16s、最多 10 次）
   → REAUTH_REQUIRED（重走渠道登录→authd→Ticket→gated→EnterGame）→ OFFLINE
4. 关键参数表：heartbeat_interval_ms=5000、miss_count=3、退避基数/上限/重试次数（05 §3.3 原表）
5. 参数必须客户端可配置：兼容有心跳/无心跳两种服务端轨
6. 视图层：toast「网络异常，已重连」；全量 SYNC_PROPS 重建视图
7. 复盘：重连=新会话要写进设计；状态机显式化；参数可配置而非硬编码
8. 已知环境限制：仅客户端状态机；未覆盖跳转途中重连；真机网络抖动未 fully 验证
9. 代码与运行：重连状态机相关脚本路径、重连取证截图索引

**配图**：封面 + 四态状态机图 + 真实重连截图
**数据说明**：参数引用 05 §3.3 原表；5000ms 等标注为默认值，非实测延迟。
