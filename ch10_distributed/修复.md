# ch10_distributed 修复记录

本文件记录实现/调试过程中踩到的真实坑，以及对应的修复。每个坑都是「先跑挂、再定位、
最后改」得来的，不是凭空设想。

---

## 坑 1：三节点全回退成 auth，抢绑 2531 集体崩

**现象**：`make test` 一启动，auth / center1 / center2 三个节点**全部**报
`Listen error` → 服务崩溃 → 上层 `skynet.call(init)` 拿到 `call failed`。

**定位**：前台单独跑 `node_b.conf`，日志却显示 `LAUNCH snlua login_gateway` 且
`Listen on 0.0.0.0 2531`。也就是说 center1 节点竟然识别成了 `auth` 角色、还去绑 2531——
而 auth 节点也绑 2531，于是 `Listen error`。

顺藤摸瓜：`runtime.lua` 里业务配置（node_name / cluster_port / center_nodes）用的是
`os.getenv("CH10_CONF") or "conf/node_a.conf"` 去**重新解析**一份 conf 文件。但 Makefile
启动每个节点时**只传了 `skynet conf/node_b.conf`（第一个参数），没设 `CH10_CONF`**，于是
三个进程全部回退到默认值（node_name=auth, port=2531）→ 都当 auth、都抢 2531。

**本质**：用「进程环境变量去猜 skynet 到底加载了哪个 conf」这件事本身就脆弱，漏传一次
就全员错乱。

**修复**：改成从 `skynet.getenv(...)` 读业务配置。skynet 启动时已经解析了它加载的那份
`.conf`，`skynet.getenv` 天然知道「当前进程是 center1 还是 auth」，不依赖任何易漏传的
环境变量。`CH10_*` 仍作为单测调参覆盖（优先级高于 .conf）。

```lua
-- runtime.lua（改后）
M.cluster      = skynet.getenv("cluster")      or "./conf/clustername.lua"
M.node_name    = skynet.getenv("node_name")    or "auth"
M.cluster_port = tonumber(skynet.getenv("cluster_port")) or 2531
M.center_nodes = skynet.getenv("center_nodes") or ""
```

**教训**：多角色共用一份代码时，角色识别必须来自 skynet 真实加载的配置，而不是靠另一套
环境变量去「镜像」解析。

## 坑 2：一致性哈希分布退化成 1000 / 0

**现象**：D6（1000 次真实登录）全部压到 center1，center2 收到 **0** 次。D1 的 100
次也是 c1=100 / c2=0。分布偏差 200%。

**定位**：虚拟节点点数本身是均衡的（center1=128 / center2=128），所以不是建表漏了节点。
问题在**哈希函数**。

原哈希是 djb2：
```lua
local h = 5381
for i = 1, #s do h = (h * 33 + s:byte(i)) % 2147483647 end
```
djb2 的雪崩性很差：**同长度字符串只改变末几位，哈希值会挤在极窄的区间里**。实测
（uid 1..1000，Python 复算）：

- `uid="1"`..`"1000"` 整体值域 `177,622 ~ 2,088,288,424`（跨 1~4 位数，所以看起来跨度大）；
- 但**同一长度的 3 位数**（`"100"`..`"999"`）全部挤在 `193,431,990 ~ 193,441,008`，
  区间宽度仅约 9000；
- 虚拟节点串 `"center1#1"`..`"center2#128"` 也都是 9 字符，同样挤在窄带
  （`center1#1`=1,688,488,461、`center2#1`=1,688,489,550，两者只差约 1000）。

由于哈希上界是 `2^31-1`（`% 2147483647`）而非 `2^32`，且 uid 与 vnode 各自扎堆成两小段，
二分查找（`pick`）在环上定位时几乎所有 uid 都落到同一侧，于是恒定命中同一个 center。
换 FNV-1a（带乘法溢出的雪崩）后，短串长串都能均匀铺开，问题消失。

**验证**：用 Python 复刻算法，uid 1..1000 → center1:999/center2:1；改成 FNV-1a 后
→ 445/555，1 万样本偏差降到 ~5%。

**修复**：`balance.lua` 改用 FNV-1a（雪崩特性好，短串长串都能均匀铺满全区间）。Lua 5.4
原生 `&` / `~`，无需 bit32：

```lua
local function hash(s)
    local hv = 2166136261
    for i = 1, #s do
        hv = (hv ~ s:byte(i)) & 0xffffffff
        hv = (hv * 16777619) & 0xffffffff
    end
    return hv
end
```

**教训**：一致性哈希的 key 哈希**必须**有雪崩特性。djb2 对短输入分布极差，用它既做
key 哈希又做 vnode 哈希时，短 key 会集体退化。这是实现一致性哈希最经典的坑之一。

## 坑 3：读 center 统计走带熔断的封装 → 索引 nil 崩

**现象**：D4 熔断用例跑到 D4.4 `post2.ping` 处 `[FATAL] attempt to index a nil value
(local 'post2')`。

**定位**：`cstat("center2")` 原来走的是 gateway 的 `center_call`（即 `dist.call`，带
熔断 + 超时）。而 D4.1~D4.3 已经把 center2 的熔断器打到了 `open`，于是 D4.4 读统计时
`dist.call` 直接 `circuit_open` → `cstat` 返回 nil → `post2.ping` 索引 nil 崩。

**顺带又踩一个**：第一版 `cstat` 用 `local ok, pack = pcall(cluster.call, ...)`。但
`cluster.call` 返回的是**远端的多返回值** `(true, stats_table)`，pcall 外层再包一层成功
标志，于是实际返回 `(true, true, table)`——我只接了前两个，第二个 `true` 被当成 pack，
下游同样崩。

**修复**：
1. 监控/统计读取**绕过业务熔断器**，用裸 `cluster.call` 直连 center（center 本身健康，
   裸调用永远能拿到真实统计）。
2. 正确 unpack 多返回值：

```lua
local function cstat(node)
    local ok, r1, r2 = pcall(cluster.call, node, "@center", "stats")
    if not ok then return nil, tostring(r1) end
    if not r1 then return nil, tostring(r2) end   -- 业务层 false
    return r2
end
```

**教训**：可观测性的读取通道不能和业务调用共用同一条带熔断的链路；`pcall` 包裹一个返回
多值的函数时，要 unpack 出完整返回列表，不能直接当单值接。

## 坑 4（对照验证）：裸 cluster.call 会永久挂死

不是 bug，而是**被显式证明的危险行为**，用来衬托 `dist_call` 的必要性。

`test/test_hang.lua` 发起一次没有任何超时保护的 `cluster.call("center1","@center","hang")`，
目标服务的 `hang` 命令 `skynet.wait()` 永不返回。结果整个调用协程（连同 main）永久阻塞。
Makefile 用 `timeout 15` 把它强杀，退出码 124 即证明「确实挂死了」。

对照：`make test` 的 D3.1 用 `dist_call` 包装后，同样场景在 **993.9ms（设定 1000ms）**
内返回 `timeout`，进程继续正常服务其他请求。

**结论**：跨节点调用**永远**不能裸用 `cluster.call` 同步等待，必须包超时（至少）+ 熔断。
