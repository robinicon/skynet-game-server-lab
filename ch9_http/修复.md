# ch9_http 修复记录

---

## 1. 跨服务传函数（踩了两次）

**现象**：`register_local_metrics(name, fn)` 和 `register_gm(name, fn)` 调用后
返回 `-1`（`ERR_INTERNAL`），没有任何有用的错误信息。

**原因**：**Lua 函数无法跨服务序列化**。`skynet.call` 传函数会在序列化阶段失败，
而失败被骨架捕获成 `ERR_INTERNAL`，调用方只看到一个 -1。

**修复**：改成**间接引用**：

| 原 API | 新 API | 说明 |
|---|---|---|
| `register_local_metrics(name, fn)` | `register_metrics(name, addr, cmd)` | 传服务地址 + 命令名，服务端内部 call |
| `register_gm(name, fn)` | `register_gm(name, module_path)` | 传模块路径，服务端内部 require |

第二次踩同样的坑说明：**"跨服务只能传值"这条规则要在 API 设计阶段就落地**，
不能等到调用时才发现问题。而且错误信息被骨架吞成 `-1` 后极难排查。

**改动的附带收益**：GM 命令以模块形式提供后，模块可以被热更替换（ch12）。

## 2. `#failed` 对字符串键的表恒为 0

**现象**：注册一个会失败的 provider 后，`/health` 仍返回 `status: "healthy"`，
`provider_errors` 字段完全不出现。

**原因**：

```lua
local failed = {}
failed["broken"] = "-1"
if #failed > 0 then            -- ← 恒为 0！字符串键不计入 `#`
    body.provider_errors = failed
end
local ok = (#failed == 0)      -- ← 因此永远是 true
```

`#` 只对**连续整数键**的数组有效。对 hash 表求 `#` 是未定义/0。

这是本系列第二次遇到（第一次是 ch4 的 gate 用 `#agents` 统计在线数，恒为 0）。

**修复**：用显式计数器 `n_failed`，每次写入 `failed[name]` 时递增。

**教训**：**只要表的键不是连续整数，就不要用 `#`**，用计数器。

## 3. 漏掉 `require "shared.error_code"`

**现象**：`/health` 的 provider 全部失败，错误信息是
`attempt to index a nil value (global 'error_code')`。

**原因**：`register_metrics` 里用了 `error_code.ERR_INTERNAL`，但文件顶部没有 require。

**说明**：之所以能被快速发现，是因为 §2 修复后 `provider_errors` 会把真实原因带出来。
这两个 bug 是连锁的——**先有可观测性，才能快速定位**。

---

## 4. accept 后必须 `socket.start(fd)` 才启用读

**现象**：与 ch4 的 `gateserver.openclient(fd)` 同源——
accept 回调里只拿到 fd，不调用 `socket.start(fd)` 则该连接永远不会收到数据。

**修复**：

```lua
socket.start(listen_id, function(fd, _)
    socket.start(fd)          -- 必须：启用该 fd 的读
    ...
    socket.close(fd)
end)
```

---

## 5. `socket.listen` 的 backlog 必须显式设置

默认 backlog = 32，并发探活（`/health` 被负载均衡高频调用）时会丢弃 SYN。
与 ch4 完全相同的坑，显式设 128。
