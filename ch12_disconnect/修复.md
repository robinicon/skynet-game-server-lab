# ch12_disconnect 修复记录

本文件记录实现/调试过程中踩到的真实坑，以及对应的修复。ch12 比 ch11 省心——它是单节点、无
cluster，但仍有几个典型陷阱。

---

## 坑 1：bootstrap 写成 "snax bootstrap" → Bootstrap error

**现象**：`make test` 一启动就报 `Bootstrap error : snax bootstrap`，进程直接退，日志只有
snax.so 加载失败。

**定位**：skynet 的 `bootstrap` 配置项是「loader 服务 + 启动脚本名」，标准写法是
`bootstrap = "snlua bootstrap"`（用 `snlua` 这个 Lua loader 去跑 `bootstrap.lua`）。我误写
成 `snax bootstrap`——它试图用 `snax` 作为 loader，但本仓库编译的 skynet 没有 `snax.so`，
于是 `try open snax failed` → bootstrap 失败 → 进程退。

**修复**：改成标准值 `snlua bootstrap`。

```lua
-- conf/node.conf（改后）
bootstrap = "snlua bootstrap"
```

**教训**：`bootstrap` 的 loader 必须是 `snlua`（或你确实编译了的 loader）。抄配置时别把
`snlua` 手滑成 `snax`。

## 坑 2：Agent 没绑定到 Gate → 断线/重连静默失效

**现象**：T1.1 `断开后 offline` FAIL、T2.3 `fd 已更新为新 fd(2999)` FAIL、T3 整组
（exit/存盘）全部 FAIL，但 T1.2/T2.1/T2.2 却 PASS。

**定位**：第一版 `agent_reconnect.spawn` 只做了 `register`（向 hotfix_mgr 注册）和加载逻辑，
**忘了把 Agent 自己 bind 到 gate**。于是 `gate.disconnect(fd)` 在 `fd_to_agent[fd]` 里查不到
记录 → 直接 `return false`，**根本没给 Agent 发 `on_disconnect`**。

连锁反应：
- `on_disconnect` 没被调用 → `online` 永远是 `true` → T1.1 FAIL。
- 没启动超时定时器 → 永远不会 `save_and_exit` → T3 全 FAIL（agent 不 exit、不存盘）。
- T2.1/T2.2 为啥还能 PASS？因为 `online` 本来就是 `true`（断线没生效），重连也没生效，
  `online==true` 和「仍存活」自然成立——是「错得碰巧对了」，而不是真重连成功；真重连要
  看的 T2.3（fd 换成 2999）就露馅了。

**修复**：`spawn` 末尾让 Agent 自己 `bind` 到 gate（和 ch11 的 agent 一致）：

```lua
-- agent_reconnect.lua（改后）
function CMD.spawn(cfg)
    ...
    skynet.call(hfm, "lua", "register", skynet.self())
    -- 把自己绑定到 gate（fd → 本 agent），否则 gate.disconnect/reconnect 找不到本 agent
    skynet.call(gate, "lua", "bind", fd, "node_a", skynet.self())
    return true
end
```

修复后 T1/T2/T3 全绿（9 PASS, 0 FAIL）。

**教训**：任何「事件靠 gate 转发」的 Agent，上线时第一步必须是 `gate:bind`。漏了这步，所有
基于 gate 的事件（断线/重连/转发）都会静默失效——而且像 T2 那样「假绿」最危险，要盯住真正
该变化的断言（T2.3 的 fd 换新），不要被 `online==true` 这种恒真断言骗过。

## 坑 3（良性）：进程退出时的 assert traceback

**现象**：`make test` 末尾、`=== TOTAL: 16 PASS, 0 FAIL ===` 之后，日志里多了一行
`skynet.lua:375` 的 assert traceback（`[C]: in upvalue 'assert'`），但不影响测试计数与退出码（仍是 0）。
（注：Makefile 现已启用 `SHELLFLAGS = -o pipefail`，`| tee` 不再吞掉退出码，因此"退出码 0"
现在是能真实反映测试结果的门禁，不再是结构性恒 0。）

**定位**：这是 skynet 的**已知拆卸副作用**。main 在测试跑完后 `os.exit(0)` 触发 skynet 关闭
序列；关闭时若某个**已经 `skynet.exit()` 的服务**的队列里还残留一条异步消息（`skynet.send`
不保证对方存活），框架会把这条消息投递给已死服务的 dispatch，于是 `skynet.lua` 里的
`assert` 触发并打印 traceback。

本议题里，注册进 `hotfix_mgr` 的 Agent 在退出后未从列表移除，或重连/断线的异步 `send` 在
关闭瞬间仍在途中，都可能触发它。

**性质**：**良性**。它发生在所有测试断言之后、`os.exit` 的拆卸期，不改变任何测试结果
（16 PASS / 0 FAIL，pipefail 下退出码实测仍为 0），也不代表业务逻辑错误。

**可选的洁净化（未做）**：让 Agent 在 `save_and_exit` 前先 `skynet.send(hotfix_mgr, "unregister",
self)` 主动注销，并在 `hotfix_mgr` 提供 `unregister`；同时关闭时先 `skynet.sleep` 一小段让
在途消息落定再 `os.exit`。可消除该 traceback，但会增加样板代码，演示价值不大，故保留现状
并在本文注明。

## 其它几个"踩了但没翻车"的点

- **`skynet.name` 依旧不可用**：和 ch11 一样，本版本没有 `skynet.name`。Agent 寻址全部用
  `skynet.uniqueservice("hotfix_mgr")` / `skynet.self()` 传递，不依赖全局名字。
- **`exit` 前先回包**：`save_and_exit` 在定时器回调里跑（不是 `skynet.call` 处理路径），所以
  不需要 `retpack` 时序处理；但它仍用 `fork + sleep(0) + exit` 确保存盘/日志落盘，而不是裸
  `skynet.exit()` 立刻掐断。
- **热更 reload 包在 Agent 内部**：`CMD.reload` 直接 `package.loaded[path]=nil; require(path)`，
  没有外层 try/catch。若新模块语法错误，reload 会抛错——生产应在 `hotfix_mgr` 侧先预检新
  模块可 require，失败不广播，避免把坏模块推给所有 Agent。
