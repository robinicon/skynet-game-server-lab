# [Skynet 手记] 快 800 倍还是快 39 倍？双语言 ECS 的性能真相与数据边界

> **摘要**：给 1000 个实体做战斗 tick，Lua 版要 102 μs/帧，C 版只要 1.24 μs/帧——快 82 倍。但这个数字有个陷阱：如果把数据读回 Lua，成本立刻变成一帧的 39 倍。本文记录双语言 ECS 的完整实现（sparse-set + SoA）与四组关键测量，以及那个"编译优化完全无效"的意外结论。
>
> 系列文章：本系列基于《游戏服务器架构》第 4–12 章，用 cloudwu/skynet 逐章重新实现并优化。本文是第 6 章（ECS 框架），承接[第 5 章的对象池收益边界](./02-ch5-perf-对象池收益边界.md)。

---

## 一、开篇：为什么需要两套 ECS

`design.md` 的定位很明确：

- **低频**（背包、任务、装备、社交）→ Lua ECS：灵活、可读、可热更
- **高频**（战斗 tick、AOI 实时更新）→ C ECS：结构体 + 数组，零 GC

并且特别强调：**login / agent / 背包这类 CRUD 服务不使用 ECS**，保持普通模块。ECS 只在场景/战斗服务内部用。

这个划分看起来理所当然，但"高频"和"低频"的分界线到底在哪？我用数据回答。

## 二、C ECS 的三个核心设计

### 2.1 sparse-set：O(1) 定位 + 紧凑存储

```c
typedef struct {
    uint32_t cap, n;
    uint32_t sparse_cap;
    int32_t  *sparse;    /* eid → slot，-1 = 不存在 */
    uint32_t *eid;       /* slot → eid */
    float    *px, *py;   /* position */
    float    *vx, *vy;   /* velocity */
    int32_t  *hp, *maxhp;
} ecs_world;
```

```
sparse:  [-1, 0, 1, 2, -1, 3]     ← 用 eid 直接索引，O(1)
dense:   eid=[1,2,3,5]  px=[...]  py=[...]  vx=[...]   ← 连续，可遍历
```

删除用 **swap-remove**：把末尾元素搬到删除位。

```c
uint32_t last = w->n - 1;
if ((uint32_t)slot != last) {
    uint32_t moved = w->eid[last];
    w->eid[slot]   = moved;
    w->px[slot]    = w->px[last];
    /* ... 其余字段 ... */
    w->sparse[moved] = slot;      /* ← 别忘了回写 sparse，否则索引错乱 */
}
w->sparse[eid] = -1;
w->n--;
```

> swap-remove 最容易写错的就是最后那句 `w->sparse[moved] = slot`。
> 漏掉它，被搬动的实体就再也找不到了。测试用例 C15 专门验证
> "删除中间元素后，其余所有实体的数据仍正确"。

### 2.2 SoA：每个 component 一条连续数组

```c
float *px, *py, *vx, *vy;    /* 而不是 struct { float x,y,vx,vy; } 数组 */
```

遍历时只有四条流，CPU 能流水化 + 预取。AoS 则会跨过不需要的字段，cache 利用率下降。

### 2.3 零 GC

C 侧的 `malloc` 内存不参与 Lua GC。1000 实体的全部状态约 32 KB，常驻且不产生垃圾。

对比 Lua 版 `each()`：**每次迭代都要构造一张参数表**，1000 实体 × 1000 帧 = 100 万次临时分配。

## 三、实测：三层对比

同样逻辑（移动 + 边界反弹 + 血量回复），1000 实体 × 1000 帧：

| 实现 | 总耗时 | 每帧 | 每实体 | 相对 C |
|---|---|---|---|---|
| Lua 通用 `each()` | 412.65 ms | 412.65 μs | 413 ns | 333x 慢 |
| Lua 专用 `tick()` | 102.22 ms | 102.22 μs | 102 ns | 82x 慢 |
| **C `bench()`** | **1.24 ms** | **1.24 μs** | **1.2 ns** | 1x |

验收标准"C ECS 更新 1000 个 Entity < 1ms/帧"：**实测 0.00124 ms，余量 800 倍**。

### 注意 Lua 内部的 4 倍差距

`each()` 比 `tick()` 慢 4 倍，两者都是纯 Lua。差距全部来自：

```lua
-- each 每次迭代：构造 args 表 + n 次哈希查找 + unpack
local args = {}
for i = 1, n_names do
    local c = comps[names[i]]     -- 哈希查找
    args[i] = c
end
fn(eid, table.unpack(args, 1, n_names))

-- tick 直接访问字段，零临时对象
local pos = comps.position
local x = pos.x + vel.x * dt
```

**这是 Lua ECS 不能用于战斗 tick 的根本原因——不是 Lua 慢，是通用抽象慢。**

### 规模梯度（每帧 μs）

| 实体数 | Lua tick | C | 加速比 |
|---|---|---|---|
| 100 | 10.25 | 0.1525 | 67.3x |
| 1000 | 106.96 | 1.2370 | 86.5x |
| 10000 | 1145.59 | 13.6220 | 84.1x |

C 从 1000 → 10000 是 **11.0x**（理想 10x），线性度良好，无隐藏 O(n²)。

## 四、两个反直觉的发现

### 4.1 每帧一次 Lua→C 调用，开销可以忽略

真实用法是"Lua 每帧调一次 `w:update()`"，而我的 bench 是"C 内部连续跑 1000 帧"。两者等价吗？

```
-- C-internal loop :  1.350 us/frame    （C 内部连续跑）
-- per-frame call  :  1.309 us/frame    （Lua 每帧调一次）
-- per-call overhead: -0.041 us (-3.0%)  ← 在噪声范围内
```

差值小于测量噪声，说明**每帧一次跨语言调用完全不是问题**。

> 实测波动提示：这两个数都在 1~2μs 量级，微基准噪声很大。我在另一次运行中测到 per-call overhead 为 −0.923us（−38%），符号和幅度都变了——这恰恰印证了"它落在噪声里、不可作为稳定指标"的结论，而非推翻它。请以仓库 `ch6_ecs/log/` 当次日志为准。

实践含义：不必为了"省调用"去做复杂设计。每帧调一次 C，成本可忽略。

### 4.2 把数据读回 Lua，成本是一帧的 39 倍

```
-- read 1000 entities : 52.31 us (0.052 us/entity)
-- vs one C frame     :  1.350 us
-- ratio: 39x
```

**读一遍全部实体，比算一帧贵 39 倍。**（历史实测倍数；本轮复测约 24×——绝对值随环境波动，但"读回比算一帧贵一到两个数量级"的结论稳定。）

所以"C 比 Lua 快 82 倍"这个数字是有前提的。真实约束是：

> ✅ 把整个 system（移动 + 碰撞 + 伤害 + 死亡判定）都放在 C 里
> ✅ 只把**需要广播给客户端的增量**回传 Lua
> ❌ 不要在 Lua 里逐实体遍历 C 的数据——哪怕只是"读一下"

如果业务确实需要每帧全量同步（比如广播 AOI 状态），正确做法是让 C 直接产出打包好的二进制 buffer，Lua 只做转发，而不是 Lua 逐个 `get` 再打包。

## 五、一个意外的结论：`-O3` 完全没用

| 编译选项 | 每帧耗时 |
|---|---|
| `-O2` | 1.24 ms / 1000 帧 |
| `-O3` | 1.24 ms / 1000 帧 |

**完全一致。**

分析下来，这个循环不是指令数受限，而是：

- **内存访问模式受限**：1000 实体 × 8 个数组 ≈ 32 KB，恰在 L1 cache 边界附近
- **分支预测命中率极高**：边界检查几乎不触发（大部分实体在界内），预测全中

此时再多的指令级优化也没有收益。

> **优化 SoA 遍历要靠数据布局，不是编译器开关。**
> 想再快，方向是减少数组数量（合并字段）、缩小数据类型（float→int16）、
> 或者做数据分包让工作集进 L1——而不是加 `-O3 -march=native`。

## 六、过程中踩的坑：引用语义让断言永远成立

写测试时遇到一个很有代表性的问题：

```lua
local before = w:get(1, "position")   -- 返回 component table 的引用
w:tick(1.0, 1000)
local after  = w:get(1, "position")   -- 同一个 table！
check("tick moves position", math.abs(after.x - before.x - 1.0) < 1e-6, ...)
```

`get()` 返回的是**引用**，`before` 和 `after` 指向同一张表。tick 之后 `before.x` 也变了，差值恒为 0。

更隐蔽的是：如果把断言写反成"应该相等"，它也会通过——**引用语义会让任何对比断言失效**。

修复很简单，快照必须是标量：

```lua
local before_x = w2:get(1, "position").x
w2:tick(1.0, 1000)
local after_x  = w2:get(1, "position").x
```

**规则：涉及"变化前后对比"的断言，快照必须是标量，不能是引用。**

另一个小插曲：初版测试选了一个只有 `position`、没有 `velocity` 的实体来测"tick 后移动"，结果当然不动。这不是实现 bug，是**测试选错了对象**——但我把它保留下来变成了一条正向断言 L10b："没有 velocity 的实体不应被移动"，反而补上了组件过滤的覆盖。

## 七、结论

**1. 分界线在"每帧" vs "每次事件"**
每帧执行的逻辑用 C，事件驱动的逻辑用 Lua。中间地带看实体数量：100 实体以下 Lua 专用 tick 也能接受（10 μs/帧）。

**2. C ECS 的收益依赖"数据不外流"**
计算 1.24 μs，回传 52 μs。设计时必须保证 system 完整在 C 内。

**3. Lua 侧的 4 倍差距来自抽象，不是语言**
`each()` vs `tick()` 差 4 倍。高频路径别用通用遍历。

**4. 编译优化级别对这个场景无效**
先看数据布局和 cache，别急着加编译选项。

## 八、复盘：五条可复用的经验

**1. "快 82 倍"这种数字一定要带上前提**
C 版算一帧 1.24 μs、读回 Lua 要 52 μs（39×）。只报"快 82 倍"而不提"数据不外流"，是在给读者埋坑。任何跨语言性能对比，先问一句：数据在哪算、结果要不要传回来。

**2. Lua 慢的往往不是语言，是通用抽象**
`each()` 比专用 `tick()` 慢 4 倍，差距全在"每次迭代构造 args 表 + 哈希查找 + unpack"。高频路径要写死字段访问，别用反射式的通用遍历。

**3. swap-remove 别忘了回写 sparse**
删除中间元素时，被搬到末尾的实体的 `sparse[eid]` 必须更新到新 slot，否则那个实体再也定位不到。这类"搬移 + 索引回写"的 bug 不崩溃，只是数据静默错乱。

**4. 断言做"变化前后对比"时，快照必须存标量**
`get()` 返回的是引用，`before`/`after` 指向同一张表，差值恒为 0——甚至把断言写反也会通过。存 `before.x` 的数值，别存表引用。

**5. 优化 SoA 遍历靠数据布局，不靠编译开关**
`-O2` 和 `-O3` 实测完全一致，因为瓶颈是 32 KB 工作集的 cache 行为和高命中率的分支预测，不是指令数。想再快要减少数组数量、缩小数据类型、让工作集进 L1。

## 九、已知环境限制（重要）

- 本文性能数字（C 版 1.24 ms/帧、读回 39×、`-O3` 无收益、规模梯度）为 **WSL Ubuntu 上的历史实测记录**，测量方法与断言均可在仓库复现；绝对值随 CPU / 编译器 / 环境波动。读回倍数在本轮复测约 24×，"读回比算一帧贵一到两个数量级"的结论稳定，具体请以 `ch6_ecs/log/` 下当次日志为准。
- **微基准噪声大**：per-frame call overhead 在 1~2 μs 量级，另一次运行测到 −0.923 μs（−38%），符号和幅度都可能变——它落在噪声里，不可作为稳定指标。
- C 侧 `malloc` 内存不参与 Lua GC，1000 实体约 32 KB 常驻；这是"零 GC"结论的前提，换更大实体规模需重新评估 cache 边界。
