# ch5_perf 修复记录

> 对象池实现与基准测试过程中发现并修复的问题。

---

## 1. 闭包特化后 `:` 调用把 self 当成第一个参数（致命）

**现象**：场景 B/C/D 的 `created` 恒等于循环次数（100,000），`alloc reduction` 为 0.00%，
池化反而更慢。而场景 A 看起来"正常"。

**原因**：为了做性能优化，池的 `get` / `put` 被特化为闭包（状态放在 upvalue 里）：

```lua
api.put = function(obj)      -- 期望：obj = 业务对象
    ...
end
```

但调用方用的是方法语法 `p:put(o)`，Lua 会把它展开为 `p.put(p, o)`——
**`self`（池对象本身）成了第一个实参**，闭包里的 `obj` 拿到的是池的 api table。

后果链：
```
owned[api_table] == nil  →  判为 foreign object  →  put 返回 false
        ↓
对象从未归还  →  池永远为空  →  每次 get 都走 factory
        ↓
created == 循环次数，池化收益归零且更慢（多了一次失败的 put）
```

**修复**：所有 api 闭包统一加 `self` 首参，与 `:` 调用约定对齐：

```lua
api.get = function(_) ... end
api.put = function(_, obj) ... end
api.prewarm = function(_, n) ... end
api.stats = function(_) ... end
```

**为什么这个 bug 特别危险**：它不报错、不崩溃，只是让池静默退化为"每次新建"。
如果只看 CPU 耗时很容易误判为"池化没收益"，实际上是实现错了。
这也是为什么要用 `alloc reduction`（`created` 次数）而不是耗时作为首要验收指标——
**耗时可能被掩盖，`created` 不会说谎。**

## 2. `api.prewarm(opts.prewarm)` 用 `.` 调用导致预热数量丢失

**现象**：`prewarm = 32`，但 `stats().created` 只有 1。

**原因**：同 #1。`api.prewarm` 改为 `function(_, n)` 后，
`M.new` 内部的 `api.prewarm(opts.prewarm)` 把 32 传给了 `_`，真正的 `n` 是 nil → 预热 0 个。

**修复**：内部调用也改用方法语法 `api:prewarm(opts.prewarm)`。

**教训**：改成闭包特化时，**内部调用点和外部调用点要一起改**，只改定义会留静默 bug。

## 3. 测试用例预期写错（两处）

| 用例 | 错误预期 | 实际 | 正确解释 |
|---|---|---|---|
| T17.2 | `reused=4` | `10` | 每次 `get` 后立即 `put`，池始终非空，10 次全部命中复用；`created` 恒为预热的 4 |
| T18.2 | `size=64`（max） | `16`（prewarm） | 顺序借还时池大小稳定在**预热数**，不会涨到 `max`；`max` 是上限水位，不是目标水位 |

**说明**：这两处是**测试的预期写错**，不是实现 bug。修正后 59 用例全通过。
记录在此是因为它们反映了一个容易混淆的点：`max` 与 `prewarm` 的语义差别。

## 4. `debug.sethook` 是 per-coroutine 的（profiler 适用边界）

**现象**：对含 `skynet.call`（会 yield）的代码块做采样，拿不到任何样本。

**原因**：Lua 5.2+ 的 debug hook 是 **per-thread（per-coroutine）** 的，
`debug.sethook` 只影响当前协程；一旦 yield 切走，采样就中断。
skynet 的每个消息处理都在独立协程里。

**处理**：在 `shared/profiler.lua` 顶部明确标注适用边界——
只用于**不 yield 的同步代码块**（基准循环、纯计算）。
要 profile 含 yield 的异步流程，应在每个协程内分别 start/stop，
或改用服务级的 `skynet.stat("cpu")`（skynet 内置 profile，只有这一层）。

## 5. 认知修正：小对象池化是负优化（非 bug，但影响设计）

**现象**：场景 A（packet，5 个标量字段）strict 模式 speedup = **0.81x**（更慢）。

**分析**：池化收益 = 省下的构造成本 − (取用成本 + 归还成本)。

| 项 | packet（5 标量） | aoi_entity（含嵌套数组） |
|---|---|---|
| 构造成本（factory） | 1 次 table 分配 | 2 次 table 分配 |
| 取用+归还成本 | 数组读写 + reset + 检测 + 统计 | 相同 |
| 净收益 | **负** | **正（1.31x）** |

结论：决定池化收益的不是"字段数量"，而是**构造时的分配次数**。
纯标量小对象构造极便宜，池的取还开销反而更大。

**处理**：没有掩盖这个结果，而是把它固化成测试用例：
- 场景 A 断言"至少有一档模式不慢于非池化"（bare 1.02x 通过）
- 场景 C 断言"确实检测到了负优化"（0.93x 通过）

**收益**：产出了一条可执行的决策规则（见 README "该不该池化"）。
