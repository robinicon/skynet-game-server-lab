# ch11_jump 修复记录

本文件记录实现/调试过程中踩到的真实坑，以及对应的修复。每个坑都是「先跑挂、再定位、
最后改」得来的，不是凭空设想。ch11 的坑比 ch10 更集中在「跨进程边界」的语义差异上。

---

## 坑 1：漏 require skynet.manager 导致 skynet.name 为 nil → init service failed

**现象**：`main.lua` 里写了 `skynet.name("GATE", gate)` 给 gate 起个全局名字，节点启动即
报 `init service failed`（`attempt to call a nil value (field 'name')`），进程直接 FATAL。

**定位**：`skynet.name` 并不在 `require "skynet"` 返回的基础 API 表里，而是由
`require "skynet.manager"` 注入（见 `skynet/lualib/skynet/manager.lua:59`）。
ch11 的 `main.lua` 当时只 `require "skynet"`，没 require manager，所以 `skynet.name` 是 nil。
（对照：ch10 的 `main.lua:12` 有 `require "skynet.manager"`，所以那里的 `skynet.name("CENTER", ...)`
一直正常——这也反过来证明了 API 本身是存在的。）

**修复**：去掉 `skynet.name`。测试只用 service handle（或 cluster 注册名 `@scene_X`），
不需要进程内全局名字。若确实要全局可查：先 `require "skynet.manager"` 再用
`skynet.name("GATE", gate)`——但本议题 gate 是单例、handle 直接透传，register 都没必要。

```lua
-- main.lua（改后）
local gate = skynet.newservice("gate_redirect")
skynet.call(gate, "lua", "init", { node_name = "node_a" })
-- 不再 skynet.name("GATE", gate)
```

**教训**：`skynet.name` 属于 `skynet.manager` 扩展，不是 `skynet` 核心 API——用到它之前必须
`require "skynet.manager"`。报 "nil value" 时先查 require，而不是先怀疑 API 被删。

## 坑 2：agent 在 call 处理里直接 skynet.exit() → 调用方 call failed

**现象**：旧 agent 的 `jump` 命令里最后直接 `skynet.exit()`，测试方发起
`skynet.call(a, "lua", "jump", ...)` 拿到 `call failed`，T1/T2 全 FAIL。

**定位**：`skynet.call` 是「发请求 + 等回包」。`jump` 在同步处理里**没 `retpack` 就把服务
退出了**，调用方永远等不到回包，框架判定 `call failed`。这和 ch4 的「服务在 call 里 exit
必须先回包」是同一类坑。

**修复**：「先 return 再 fork 退出」——让 `retpack` 先生效，再在下一拍杀掉自己：

```lua
-- agent_jumper.lua（改后）
skynet.call(gate, "lua", "rebind", fd, target_node, taddr)
online = false
skynet.sleep(0)   -- 让 rebind 的重放先跑完
skynet.fork(function() skynet.sleep(0); skynet.exit() end)
return true        -- 先正常回包
```

**教训**：任何在 `skynet.call` 处理路径上要退出服务的逻辑，都必须「retpack 之后」再 exit；
`fork` 一个延迟一拍的协程是最稳的写法。

## 坑 3：跨节点用数字 handle 做 cluster.call 重绑 → 静默失效 / call to invalid address

**现象（最初版本）**：跳转方在 node_a 发起
`cluster.call("node_a", gate_handle, "rebind", fd, "node_b", new_addr)`，
想让 node_a 的 gate 把 fd 重绑到新 agent。结果要么「静默不生效」（fd 仍指向旧 agent），
要么报 `call to invalid address`。

**定位**：`gate_handle` 是 node_a 进程内的**数字 service handle**。跨节点用 cluster 通道投递
一个「目标节点本地的数字 handle」语义是不可靠的——cluster 通道按你给的地址当「目标节点上的
handle」去路由，但实际那是 node_a 的 handle，在 node_b 的命名空间里要么是无效的、要么指向
一个无关的 service。

**修复（架构级）**：把「fd 重绑」这个动作**收回到本节点做**。scene_host（在目标节点）只负责
「创建新 agent 并返回它的地址」，不做任何跨节点重绑；跳转方（旧 agent，与 gate 同节点）拿到
新地址后，用**本地** `skynet.call(gate, "lua", "rebind", fd, target_node, addr)` 完成重绑。

```lua
-- scene_host.lua：accept 只返回新 agent 地址，不碰 gate
function CMD.accept(uid, fd, state, from_node, gate)
    local a = skynet.newservice("agent_jumper")
    skynet.call(a, "lua", "spawn", { uid=uid, fd=fd, gate=gate,
                                     node_name=my_node, scene=scene_name, state=state })
    agents[uid] = a
    return true, a     -- 只返回地址；节点名由跳转方自己已知
end

-- agent_jumper.lua：拿到地址后本节点重绑
skynet.call(gate, "lua", "rebind", fd, target_node, taddr)
```

**教训**：跨节点通信的「寻址单位」应当是 cluster 注册名（`@name`）或「目标节点上有效的 handle
+ 目标节点名」组合；**永远不要**把本节点的数字 handle 当跨节点参数去发起 `cluster.call`。
重绑 fd 这种「与 gate 同节点」的操作，本地 `skynet.call` 一把梭最稳。

## 坑 4：cluster.call 多返回值跨边界错位 → 把成功标志当成了地址

**现象（最早一版）**：scene_host 返回 `(true, a)`，但 agent 用
`local ok, taddr = pcall(cluster.call, ...)` 只接两个值。T1.2 打印
`fd 重绑到新 agent (node=true, new=true)`——`new` 竟是布尔 `true`，随后
`skynet.call(true, ...)` 崩 `dest address type (boolean) must be a string or number`。

**定位**：`cluster.call` 返回的是 scene_host 的多返回值 `(true, a)`。pcall 再包一层成功标志，
实际返回 `(true, true, a)`——agent 只接了前两个，第二个 `true`（成功标志）被当成新 agent
地址 `taddr`，存进 gate 的 `fd_to_agent[fd].addr`，于是后续所有转发/查询都拿 `true` 当地址。

**修复**：按 `(ok, success, address)` 三值解包，且**不要依赖跨边界多返回值的「节点名」**：

```lua
-- agent_jumper.lua（改后）
local ok, success, taddr = pcall(
    cluster.call, target_node, "@scene_" .. target_scene, "accept",
    uid, fd, s, node_name, gate)
if not ok or not success or not taddr then
    skynet.call(gate, "lua", "rebind", fd, node_name, skynet.self())  -- 回滚
    return false, "jump_failed:" .. tostring(taddr)
end
skynet.call(gate, "lua", "rebind", fd, target_node, taddr)  -- 用已知的 target_node
```

> 注意 `target_node` 是跳转方**自己已知**的目标节点名（jump 的入参），而不是从
> `cluster.call` 的多返回值里「赌」一个节点名出来——同节点 `cluster.call` 返回顺序/数量与跨
> 节点可能不一致，跨边界依赖多返回值的第二/第三值极易错位。

**教训**：跨边界解包多返回值时，把「协议约定的固定字段（这里是地址）」显式 unpack 出来，并
用调用方已知的上下文（target_node）补全节点名，**不要跨边界赌返回值的顺序和数量**。

## 坑 5：gate_redirect 里 route 是前向 local 引用 → 调用时 route 是 nil（全局）

**现象**：T3 窗口期重放时崩
`gate_redirect.lua:46: attempt to call a nil value (global 'route')`，replay 失败 → T3.2
`received=0`。

**定位**：`route` 用 `local function route(...)` 在 **当时第 51 行** 才声明，而 `CMD.rebind`
在 **当时第 46 行** 就调用它（行号为修复前版本；修复后 route 前移到第 22 行、CMD.rebind 在第 58 行）。Lua 里 `local` 的作用域**从声明行的下一行**才开始——代码在声明行
之前的引用看不到这个 local，于是 `route` 被当成**全局变量**解析（全局 `route` 为 nil）→ 调用
nil 崩。这是 Lua 最经典的前向引用陷阱。

**修复**：把 `route` 的定义**移到所有 `CMD.*` 之前**（模块顶层，紧跟 `fd_to_agent` 声明之后），
保证 `CMD.rebind` / `CMD.forward` 引用它时 local 已在作用域内：

```lua
-- gate_redirect.lua（改后结构）
local fd_to_agent = {}

local function route(fd, msg)   -- 先定义
    ...
end

local CMD = {}

function CMD.rebind(fd, node, addr)
    ...
    for _, msg in ipairs(buf) do
        route(fd, msg)          -- 现在 route 是有效的 local
    end
end
```

**教训**：在 Lua 里，被多个函数互相调用的工具函数（尤其是被位于其声明之前的代码调用）要
**前置声明**，或者至少放在所有调用者之前定义。前向 `local function` 不会像某些语言那样自动
提升到作用域顶部。

## 运行方式上的坑（WSL 多进程）

- **严禁 `pkill -f skynet`**：测试需要 node_a + node_b 两个进程。曾经用 `pkill -f "skynet/skynet"`
  清残留，结果把 WSL bash 自身也杀了（它的命令行里含这些串）→ exit 9/126。改为：主 shell
  后台起 node_b 并 `echo $$! > log/node_b.pid` 捕获 PID，结束 `kill $PID`。
- **残留进程占端口**：node_b 残留会占 2542 → node_a 连不上 → `Listen error`。每次 `make test`
  开头先 `rm -f log/*.log` 并确保没有残留 node_b（单独 `timeout 4` 验证 node_b 能正常监听
  2542 后再跑主测试）。
