# ch6_ecs 设计取舍与性能实测

> 依据：design.md Phase 3 —— 低频用 Lua ECS，高频用 C ECS
> 验收标准：**C ECS 更新 1000 个 Entity < 1ms/帧**

---

## 0. 一句话结论

C ECS 每帧 **1.24 μs**（1000 实体），是验收标准（1 ms）的 **1/800**。
比 Lua 专用 tick 快 **82 倍**，比 Lua 通用 `each()` 快 **333 倍**。

但真正的结论不是"C 快"，而是：**C ECS 的快有一个前提——数据必须留在 C 里。**
把 1000 个实体的数据读回 Lua 要 52 μs，是一帧计算成本的 **39 倍**。

---

## 1. 为什么分两套 ECS

| 维度 | Lua ECS（低频） | C ECS（高频） |
|---|---|---|
| 场景 | 背包、任务、装备、社交 | 战斗 tick、AOI 实时更新 |
| 频率 | 事件驱动（每秒几次） | 每帧（30~60 fps） |
| 数据结构 | table 挂接，灵活可变 | SoA 数组，布局固定 |
| 可热更 | ✅ Lua 可重载 | ❌ 需重启或 dlclose |
| 可读性 | 高 | 低 |
| 本例每帧（1000 实体） | 102 μs（专用）/ 413 μs（通用） | 1.24 μs |

`design.md` 明确要求：**login / agent / 背包等 CRUD 服务不使用 ECS**，保持普通模块。
ECS 只在场景/战斗服务内部使用。

---

## 2. C ECS 的三个核心设计

### 2.1 sparse-set：`sparse[eid] → slot` + dense 数组

```
sparse:  [-1, 0, 1, 2, -1, 3]   eid 索引，O(1) 定位
dense:   eid=[1,2,3,5]  px=[...]  py=[...]  vx=[...]  ...
```

删除用 **swap-remove**：把末尾元素搬到删除位，O(1) 且保持数组紧凑。
测试用例 C15 专门验证了"删中间元素后其余实体数据仍正确"——这是 swap-remove 最容易写错的地方。

### 2.2 SoA（Structure of Arrays）而非 AoS

```c
float *px, *py, *vx, *vy;    /* 每个 component 一个连续数组 */
int32_t *hp, *maxhp;
```

遍历时只需要 px/py/vx/vy 四条流，CPU 可以流水化 + 预取。
若用 AoS（每个 entity 一个 struct），每次访问会跨过不需要的字段，cache 利用率下降。

### 2.3 零 GC

C 侧的 `malloc` 内存不参与 Lua GC。1000 实体的全部状态约 32 KB，常驻不产生垃圾。
对比 Lua 版：`each()` 每次迭代构造一张参数表，1000 实体 × 1000 帧 = **100 万次临时表分配**。

## 3. 实测数据（1000 实体 × 1000 帧，WSL Ubuntu）

| 实现 | 总耗时 | 每帧 | 每实体 | 相对 C |
|---|---|---|---|---|
| Lua 通用 `each()` | 412.65 ms | 412.65 μs | 413 ns | 333x 慢 |
| Lua 专用 `tick()` | 102.22 ms | 102.22 μs | 102 ns | 82x 慢 |
| **C `bench()`** | **1.24 ms** | **1.24 μs** | **1.2 ns** | 1x |

**验收结论：C ECS 每帧 0.00124 ms < 1 ms，达标（余量 800 倍）。**

### 规模梯度（每帧耗时）

| 实体数 | Lua tick (μs/帧) | C (μs/帧) | 加速比 |
|---|---|---|---|
| 100 | 10.25 | 0.1525 | 67.3x |
| 1000 | 106.96 | 1.2370 | 86.5x |
| 10000 | 1145.59 | 13.6220 | 84.1x |

C 从 1000 → 10000 实体是 **11.0x**（理想 10x），线性度良好，说明没有隐藏的 O(n²)。

---

## 4. 两个反直觉的发现

### 4.1 每帧一次 Lua→C 调用的开销可以忽略

```
-- C-internal loop :  1.350 us/frame    （C 内部连续跑 1000 帧）
-- per-frame call  :  1.309 us/frame    （Lua 每帧调一次 w:update）
-- per-call overhead: -0.041 us (-3.0%)  ← 在噪声范围内
```

差值小于测量噪声，说明**"每帧调一次 C"不是问题**。
实践含义：不必为了省调用开销而做复杂设计，每帧一次调用完全可接受。

### 4.2 但把数据读回 Lua 是灾难

```
-- read 1000 entities : 52.31 us (0.052 us/entity)
-- vs one C frame     :  1.350 us
-- ratio: 39x
```

**读一遍全部实体的成本，是算一帧的 39 倍。**

这是 C ECS 最重要的设计约束：

> ✅ 把整个 system（移动 + 碰撞 + 伤害 + 死亡判定）都放在 C 里
> ✅ 只把**需要发给客户端的增量**回传 Lua
> ❌ 不要在 Lua 里逐实体遍历 C 的数据（哪怕只是"读一下"）

如果业务确实需要每帧把全量状态同步到 Lua（比如广播给所有客户端），
正确的做法是让 C 直接产出打包好的二进制 buffer，Lua 只做转发，
而不是 Lua 逐个 `get` 再打包。

## 5. 编译优化级别的实验

| 选项 | 每帧耗时 |
|---|---|
| `-O2` | 1.24 ms / 1000 帧 |
| `-O3` | 1.24 ms / 1000 帧 |

**完全一致。** 说明这个循环不是指令数受限，而是**内存访问模式 + 分支预测**受限：

- 1000 实体 × 8 个数组 ≈ 32 KB，恰好在 L1 cache 边界附近
- 边界检查分支几乎不触发（大部分实体在界内），分支预测命中率接近 100%
- 此时再多的指令级优化也没有收益

实践含义：**优化 SoA 遍历要靠数据布局，不是靠编译器开关。**

---

## 6. 没有做的事

- ❌ **多 system 拆分**（movement / regen 分开）：合并成一次遍历更快（一次访存完成所有计算）。
  只有当不同 system 需要不同频率时才拆分。
- ❌ **SIMD  intrinsics**：可移植性差，且当前已满足验收标准 800 倍余量。
- ❌ **多线程并行 tick**：skynet 的服务模型是单线程消息循环，引入多线程会破坏这个前提。
- ❌ **ECS 用于 login / agent / 背包**：`design.md` 明确要求这些 CRUD 服务保持普通模块。
